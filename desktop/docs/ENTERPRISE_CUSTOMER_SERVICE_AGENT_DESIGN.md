# 企业级智能客服 Agent 系统设计与实施基线

> 文档状态：项目设计基线
> 适用项目：智能客服桌面端（Smart Kefu）
> 更新日期：2026-08-20
> 当前客户外部渠道：企业微信客服
> 设计图片生成后端：珍希 AI

## 1. 文档目的

本文把“企业级智能客服 Agent”从概念说明转换为本项目可实施、可测试、可审计的产品与工程方案。

系统目标不是做一个自由聊天机器人，而是建设一个受企业规则控制的业务处理系统：大模型负责理解客户、规划步骤和生成回复草稿；确定性规则、权限系统和企业业务接口负责真正执行订单、付款、退款、发货等动作。

本文同时记录当前代码已经具备的能力、仍然存在的缺口、推荐实施顺序和最终验收标准，避免重复建设或把本地验证误认为真实业务交付。

## 2. 核心产品目标

### 2.1 业务解决能力

系统应能自主完成低风险、标准化的客服任务，包括：

- 产品与政策咨询；
- 商品、订单和物流信息查询；
- 补充收集订单、预算、数量、用途和售后证据；
- 生成设计需求、报价或售后处理草稿；
- 在规则允许的范围内执行经过授权的业务操作；
- 跟踪业务结果并向客户反馈；
- 无法可靠完成时及时转交人工。

### 2.2 企业可控性

- 企业事实必须来自已审核知识、商品目录或真实业务接口；
- 大模型不得编造价格、库存、订单状态、退款金额、支付流水或处理结果；
- 所有写操作必须经过权限、身份、状态、金额和幂等校验；
- 高风险操作必须支持人工确认或双人复核；
- 企业可配置政策，但不能通过普通运行开关全局绕过身份隔离、幂等和审计要求。

### 2.3 可交接与可恢复

系统必须在以下情况主动转人工：

- 客户明确要求人工；
- 投诉、维权、法律、赔偿或高情绪场景；
- 退款、支付、订单修改等高风险操作需要审批；
- 身份、订单或会话绑定无法确认；
- 连续澄清或工具调用失败；
- 企业规则与客户诉求冲突；
- 模型、知识或业务数据不足以形成可靠结论。

转人工后，人工坐席必须能看到完整交接包，不应重新询问系统已经确认的信息。

### 2.4 高并发与高可用

- 入站消息、Agent 任务、工具执行和出站发送相互解耦；
- 相同客户会话按顺序处理，不同客户可并行；
- 业务动作使用幂等键，防止重复退款、重复下单或重复发送；
- 支持限流、超时、熔断、死信、人工补偿和恢复；
- 模型故障时可降级为规则答复、知识检索答复或人工接管。

### 2.5 可运营迭代

运营人员应能完成：

- 导入、审核、发布和下线知识；
- 配置 Agent、适用场景、话术和流程；
- 查看路由、知识命中、工具执行和人工交接记录；
- 修正错误路由和回复；
- 用真实失败案例形成回归测试集；
- 观察解决率、转人工率、首响、处理耗时和满意度。

## 3. 总体架构

```text
企业微信客户消息
        │
        ▼
接入与身份层
回调校验 / 消息同步 / 客户与会话绑定 / 幂等去重
        │
        ▼
Agent Runtime
上下文装配 → 意图与风险判断 → 任务规划 → 决策通道选择
        │
        ├── 知识回答：审核知识 + 商品事实 + 安全回复
        ├── 只读工具：订单、物流、库存、状态查询
        ├── 写入工具：预览 → 审批 → 执行 → 验证
        └── 人工交接：交接包 + 会话锁 + 待办通知
        │
        ▼
Guard / Policy
身份隔离 / 权限 / 状态机 / 金额 / 幂等 / 敏感内容 / 发送限制
        │
        ▼
持久化队列与企业微信发送
        │
        ▼
回执、审计、运营指标与离线评测
```

### 3.1 接入与身份层

本项目当前对外客户渠道以企业微信客服为准。Web 和 Electron 是员工工作台，不作为客户消息渠道。

正式入站链路应保持：

`callback → sync_msg → 客户/会话持久化 → Agent 路由 → 安全发送队列 → kf/send_msg → 回执与审计`

关键约束：

- 使用 `open_kfid + external_userid` 绑定真实客户；
- 每条消息必须有渠道事件或业务幂等标识；
- 客户、会话、企微客服账号必须同时匹配；
- 任何身份冲突都应失败关闭并转人工，不能猜测客户身份；
- API 接收成功不等于客户手机收到，最终验收必须包含回执和手机确认。

### 3.2 Agent Runtime

Agent Runtime 是统一的任务控制中心，负责：

- 装配当前消息、最近对话、客户资料、历史业务状态；
- 判断意图、场景、风险和缺失信息；
- 生成结构化任务计划；
- 选择知识回答、只读工具、写入工具或人工交接；
- 控制任务状态迁移；
- 保存可审计的决策摘要和执行证据。

大模型输出必须为结构化建议，不能直接写数据库或调用高危接口。

### 3.3 决策通道

| 通道 | 适用场景 | 是否允许自动发送/执行 |
| --- | --- | --- |
| 知识回答 | 政策、产品说明、常见问题 | 知识已审核且事实完整时可自动发送 |
| 只读工具 | 查订单、物流、库存、设计进度 | 身份匹配且工具成功时可自动回复 |
| 低风险写入工具 | 创建需求草稿、保存客户补充信息 | 通过权限、幂等和状态校验后可执行 |
| 高风险写入工具 | 退款、赔偿、订单关键字段修改、付款确认 | 必须预览并人工审批后执行 |
| 人工交接 | 投诉、争议、身份不明、连续失败、客户要求人工 | 立即锁定自动化并生成交接包 |

## 4. 任务状态机

建议新增统一的 Agent 任务状态，而不是把任务状态分散在路由、通知、发送任务和业务日志中。

```text
created
  └─→ collecting
        └─→ ready
              ├─→ awaiting_approval
              │     ├─→ approved
              │     └─→ rejected
              ├─→ executing
              │     ├─→ succeeded
              │     ├─→ failed
              │     └─→ unknown_outcome
              └─→ handed_off
```

推荐核心实体：

- `AgentTask`：一次客户业务诉求；
- `AgentStep`：任务内的规划和执行步骤；
- `ToolDefinition`：工具定义及权限策略；
- `ToolExecution`：一次真实工具调用；
- `ApprovalRequest`：人工审批记录；
- `HandoffSnapshot`：转人工交接包；
- `AgentTaskEvent`：追加式状态事件和审计证据。

每次状态迁移应验证当前版本，防止并发覆盖，并记录操作者、触发来源、前后状态和业务幂等键。

## 5. Tool Registry 设计

### 5.1 工具定义

每个工具至少包含：

```json
{
  "name": "order.query",
  "version": "1",
  "effect": "read",
  "requiredCapability": "view_orders",
  "approvalPolicy": "none",
  "timeoutMs": 5000,
  "retryPolicy": "safe_read_only",
  "inputSchema": {},
  "outputSchema": {},
  "auditFields": [],
  "sensitiveFields": []
}
```

工具必须明确：

- `effect`：`read`、`draft_write`、`business_write` 或 `external_side_effect`；
- 所需操作者权限；
- 是否需要客户确认、人工审批或双人复核；
- 输入输出 JSON Schema；
- 超时和重试规则；
- 幂等键生成规则；
- 未知结果的查询与补偿方法；
- 可写入日志的字段白名单；
- 密钥、手机号、地址、支付信息等敏感字段处理方式。

### 5.2 推荐首批工具

只读工具：

- `customer.profile.get`
- `catalog.search`
- `order.query`
- `logistics.query`
- `design.status`
- `refund.eligibility`

低风险写入工具：

- `customer.note.append`
- `design.request.create`
- `quote.draft.create`
- `after_sales.case.create`

高风险工具：

- `order.address_change.preview/execute`
- `order.cancel.preview/execute`
- `refund.preview/execute/verify`
- `compensation.preview/execute/verify`

## 6. 退款与高风险操作

退款不能设计成模型一次调用就完成，必须拆分为三个阶段。

### 6.1 Preview

- 查询真实订单和付款流水；
- 校验客户、会话、订单和企业账号绑定；
- 计算最大可退金额；
- 检查订单状态、历史退款和售后证据；
- 生成退款建议，不产生资金动作。

### 6.2 Execute

- 人工确认退款金额、原因和退款渠道；
- 高金额时执行双人复核；
- 使用唯一幂等键调用支付系统；
- 不自动重试未知结果；
- 只保存支付系统返回的真实受理编号。

### 6.3 Verify

- 查询支付系统最终状态；
- 保存支付回执和脱敏凭证；
- 更新售后任务状态；
- 生成客户回复草稿；
- 客户发送成功后记录企微回执。

当前项目售后服务已经能校验可退金额、记录退款方式和凭证，并形成支付事件和审计日志，但还没有连接真实支付退款接口。因此现阶段只能表述为“人工完成退款后，系统记录并核验结果”，不能表述为“Agent 已自动退款”。

## 7. 知识库与 RAG

### 7.1 当前基础

当前项目已经支持：

- 知识审核状态；
- Agent、企微账号、客户和会话范围隔离；
- BM25 关键词相关度；
- 中文字符 n-gram 相似度；
- 业务意图信号；
- 已知客户事实冲突排除；
- 检索原因、得分和使用决策追踪。

该能力属于本地混合检索与重排，不是向量语义检索。

### 7.2 推荐增强

- 文档来源、版本、发布日期、失效日期和负责人；
- 产品、政策、内部 SOP 分级权限；
- 文档切块和可编辑知识片段；
- 向量召回与现有 BM25 混合；
- 独立重排模型；
- 答案来源引用；
- 低置信度拒答和人工转接；
- 知识发布前测试集验证；
- 知识更新后的自动回归评测；
- 过期或冲突知识自动阻断。

只有 `ready` 且在有效期内的知识可以进入客户回复。内部会议记录必须脱敏并转换为客户知识或内部 SOP，不能直接暴露给客户。

## 8. 记忆设计

### 8.1 短期记忆

短期记忆用于当前会话和当前任务：

- 最近有效消息；
- 当前意图和业务场景；
- 已确认字段；
- 缺失字段；
- 当前任务和步骤状态；
- 最近工具结果；
- 最近已发送回复，避免重复回答。

短期记忆应有明确窗口和摘要机制，不能无限拼接聊天记录。

### 8.2 长期记忆

长期记忆只保存稳定、有业务价值且允许保存的事实：

- 客户基础资料和企业归属；
- 历史订单、报价、设计和售后；
- 已确认的偏好、用途和服务记录；
- 客户授权保存的长期备注。

不得把模型猜测、一次性情绪或未审核对话自动写成长期事实。长期记忆需要来源、置信度、更新时间、保留期和删除能力。

## 9. 人工交接

标准 `HandoffSnapshot` 应包含：

- 客户、企微客服账号和会话身份；
- 客户本轮诉求；
- 最近有效对话摘要；
- 当前情绪和风险标签；
- 已确认字段与仍缺字段；
- 使用的知识和商品事实；
- 工具调用、返回结果和失败原因；
- 当前任务状态；
- 推荐人工下一步；
- 自动化锁定原因和恢复条件。

客户明确要求人工时，应优先转接，不能继续反复发送“请描述问题”。人工处理完成后，只有在明确解除会话锁并记录处理结果后，自动化才可恢复。

## 10. 输出校验与安全策略

发送客户回复前至少执行：

1. 客户、会话和企微账号身份一致性检查；
2. 知识和业务事实来源检查；
3. 订单、金额、库存和物流数据真实性检查；
4. 敏感词、承诺、法律与售后风险检查；
5. 重复回复和跨会话内容检查；
6. 人工锁定和审批状态检查；
7. 企微发送窗口、频率和队列顺序检查；
8. 发送内容与附件绑定检查。

模型服务失败、超时或返回非法结构时，应根据场景降级：

- 已有确定性答案：发送规则或知识答复；
- 只缺信息：发送安全澄清问题；
- 涉及真实业务状态：转人工，不猜测；
- 已经提交外部动作但结果未知：停止重试，进入 `unknown_outcome` 并查询或人工核验。

## 11. 队列、并发与可靠性

### 11.1 队列拆分

推荐至少分为：

- 入站消息队列；
- Agent 任务队列；
- 工具执行队列；
- 高风险审批队列；
- 企业微信出站发送队列；
- 回执和状态核验队列；
- 死信与人工补偿队列。

### 11.2 顺序与并发

- 同一企业微信客服账号内遵守官方发送限制；
- 同一会话内按事件序号串行；
- 不同会话可并行；
- 写操作按业务对象加语义锁；
- 全局队列和单账号队列均设置上限；
- 高峰期优先处理客户入站、人工回复和回执核验。

当前项目已经配置 BullMQ/Redis durable 模式，但运行并发策略仍偏保守。后续扩容必须先完成幂等、任务状态机和账号级顺序保证，不能只增加 Worker 数量。

### 11.3 熔断降级

- 模型供应商按速度、可靠性和费用进行路由；
- 对话回复受明确延迟预算限制；
- 业务写接口禁止模型层自动重试；
- 未知发送结果禁止重复发送；
- Redis、数据库、模型、珍希 AI 或企微异常时分别熔断；
- 降级状态必须在坐席工作台可见。

## 12. 权限、隐私与审计

- 操作者采用能力权限，不信任前端传入的操作者、审批人或负责人字段；
- 每个工具使用最小权限服务身份；
- 高危操作支持金额阈值和双人复核；
- 日志只记录白名单字段，密钥和完整支付信息不得进入日志；
- 客户身份、会话、附件和业务对象必须绑定；
- 每一次写操作记录操作人、来源、输入摘要、结果、幂等键和时间；
- 支持客户数据导出、更正、保留期和删除策略；
- 不保存或展示大模型原始思维链。

审计中应保存的是可解释的决策摘要，例如：路由结果、规则命中、知识来源、工具名称、脱敏输入输出、审批人和执行结果。

## 13. 数据观测与运营指标

### 13.1 在线业务指标

- 会话量和客户消息量；
- 首次响应时间和完整解决时间；
- 自动解决率；
- 转人工率及转人工原因；
- 知识命中率和低置信度率；
- 工具成功率、超时率和未知结果率；
- 发送成功、异步失败和队列积压；
- 客户满意、中评和不满意率；
- 人工接管后再次自动化的恢复率。

### 13.2 质量评测

- 事实正确性；
- 政策一致性；
- 是否错误承诺价格、库存、时间或退款；
- 是否重复追问已知信息；
- 是否正确选择 Agent 和工具；
- 是否应转人工而未转；
- 是否跨客户或跨会话使用数据；
- 是否正确完成端到端业务任务。

“幻觉数量”不能只靠关键词统计，应由抽样质检、规则检测、客户反馈和标准测试集共同判定。

## 14. 当前项目能力对照

| 模块 | 当前实现 | 成熟度判断 |
| --- | --- | --- |
| 企业微信接入 | callback、sync_msg、客户绑定、发送和审计 | 基础完整，仍需真实手机端持续验收 |
| 客户与会话 | 客户资料、标签、备注、消息、订单关联、人工锁 | 有数据基础，缺统一记忆服务 |
| 意图路由 | 场景评分、多轮澄清、风险词、高价值线 | 可用，需继续用真实错例回归 |
| 知识检索 | 审核知识、BM25、字符相似度、状态重排 | 已超过简单关键词，尚非向量 RAG |

## 16. 最低验收标准

### 16.1 安全与正确性

- 跨客户、跨会话、跨企微账号数据泄露为 0；
- 所有写操作均有幂等键、权限校验和审计记录；
- 退款、赔偿、付款确认等操作 100% 经过规定审批；
- 未知外部结果不会自动重试；
- 模型无法直接绕过业务状态机；
- 知识未审核、已过期或存在冲突时不会用于自动回复。

### 16.2 业务闭环

- 查询类任务能从真实业务系统取数并回答；
- 写操作能完成预览、审批、执行、核验和客户通知；
- 转人工能完整传递交接包；
- 人工处理后能记录结果并安全恢复自动化；
- 每个任务可从客户消息追踪到最终回执。

### 16.3 性能与可靠性

- 常规消息快速确认接收，复杂任务异步推进；
- 队列积压、失败和死信可见且可处理；
- 同会话保持顺序，不同会话能够并行；
- 模型、企微、Redis、数据库和设计平台故障均有明确降级路径；
- 进程重启后未完成任务可以恢复。

### 16.4 外部交付证明

企业微信正式验收至少包含：

1. 真实测试客户发消息；
2. 公网回调成功；
3. `sync_msg` 拉取并持久化；
4. Agent 路由、知识或工具执行；
5. 必要的人工审批；
6. `kf/send_msg` 受理；
7. 异步失败扫描和审计；
8. 客户手机真实收到并人工确认。

本地 API 200、健康检查成功、发送接口受理或安装包哈希正确，都不能单独证明客户已经收到消息或业务动作已经在外部系统完成。
