# 个人微信多账号客服的合理实现

## 结论

个人微信没有面向客服系统的稳定官方服务端接口。正式生产环境应优先使用企业微信的微信客服、客户联系或公众号/小程序客服能力；个人微信只能作为受人工监督的兼容通道，不能以规避平台规则、隐藏机器人身份或模拟真人行为为目标。

本项目不把微信原生窗口强行重新挂载到 Electron 窗口。Windows 原生窗口重挂载会造成焦点、剪贴板、输入法、缩放、升级兼容和崩溃恢复问题，也不能把第三方客户端变成受支持的 API。软件内应展示统一的客户、会话和审批视图；官方微信客户端以独立伴随窗口运行，需要人工接管时再定位并唤起绑定窗口。

## 推荐通道优先级

1. 企业微信微信客服/客户联系等官方 API：生产主通道，可审计、可扩展。
2. 公众号或小程序客服接口：适合已有公众号/小程序入口的客户会话。
3. 个人微信受监督兼容通道：只用于低规模、明确授权、人工审批场景，默认禁止真实发送。

腾讯当前政策入口：<https://www.tencent.com/zh-cn/policies/>。企业微信开发能力应以企业微信官方开发者中心当期文档为准：<https://developer.work.weixin.qq.com/>。

## 系统结构

```text
客服工作台（Next.js）
        |
        v
控制平面（NestJS）---- 审批、账号策略、审计、全局停止
        |
        v
账号任务队列 ---- 每账号租约 ---- 同 Windows 会话串行锁
        |
        v
本机实例代理（每个 Windows 会话一个）
        |
        +---- 独立 loopback 端点和令牌
        +---- 微信账号/进程/窗口/Windows 会话身份复核
        +---- 最近客户消息证据复核
        +---- 发送后观察与 ACK
        |
        v
官方微信桌面客户端（独立伴随窗口）
```

## 当前代码审计

已经具备：

- `personal-wechat-rpa.service.ts` 支持多实例注册、每账号独立 loopback endpoint/token 和停用状态。
- `USE_LOCAL_STORE=false` 时，认证后的注册表 `wechatAccountId` 作为 `WechatAccount.id`，个人微信账号、客户、会话、入站消息、业务绑定和审计通过 Prisma 事务持久化；生产路径不会回退到 LocalStore。
- 本机 endpoint/token、进程、窗口、Windows 会话和配置路径只留在主机注册表，Prisma 业务表、审计明细和绑定接口响应均不保存这些主机凭据。
- `personal-wechat-bridge.js` 已按 Windows 会话分组；同一会话的出站任务串行，不同会话可独立处理。
- RPA Host 在发送前核对账号、进程、窗口、Windows 会话、聊天标题和最近客户消息，并在发送后观察聊天历史再确认结果。
- `wechat-dispatch.service.ts` 已有人工接管和任务暂停能力。

进入多账号生产试点前仍需补齐：

- 实例心跳、实时能力探测、账号/端点/Windows 会话唯一性约束和任意 N 个实例的 supervisor。
- 同 Windows 会话覆盖入站扫描、窗口探测和出站发送的统一仲裁器；不能只锁发送动作。
- 在真实 PostgreSQL 预发布环境完成 migration、并发首次绑定、唯一冲突和幂等重放验收；仓库内 fake Prisma 契约测试不等于生产数据库证据。
- 一次性 `operationId + attemptId + expiresAt + nonce`，阻止本机发送请求被重复执行。
- `UNCERTAIN_QUARANTINED` 未知投递状态；进入实际交互后若无法证明送达，禁止自动重试。
- 每账号业务预算、静默时段、客户退订、敏感场景人工审批、连续失败熔断和全局停止。
- 凭据从运行时明文 JSON 迁移至 Windows Credential Manager、DPAPI 或 Electron `safeStorage`，配置文件只保存引用。
- RPA 健康状态与 `/send` 能力必须使用同一个发送开关，不能出现健康接口声称关闭但端点仍执行发送。

## 多账号隔离

- 一个账号绑定一个逻辑账号 ID、微信昵称、OwnerWxId、进程、窗口句柄、Windows 会话、loopback 端点和令牌；逻辑 ID、昵称、OwnerWxId 和令牌在启用与停用实例之间都必须唯一。
- 同一 Windows 桌面会话共享焦点、剪贴板和输入资源，只允许串行操作，不能声称并行发送。
- 需要真正并行时，每个账号使用独立 Windows 用户会话、远程桌面会话或隔离虚拟机，并为每个实例分配独立端点和凭据。
- 调度任务必须同时绑定账号、客户、会话、最近一条客户消息和发送尝试 ID；任何证据变化都要重新人工确认。
- 实例离线、窗口不匹配、身份不匹配、最近消息变化或发送结果不明确时立即隔离，不自动重试。

## 发送状态机

```text
draft
  -> pending_review
  -> approved
  -> queued
  -> preflight
  -> sent_ack

preflight -> blocked
preflight -> failed
preflight -> uncertain -> quarantined
```

- `uncertain` 不是普通失败；它表示无法证明消息是否送达，只能隔离并人工核验。
- 启用真实发送必须是受权限控制的服务端动作，前端不得直接翻转开关。
- 全局停止、账号停止和人工接管都必须阻止新任务入队。
- 每账号预算是明确的业务上限和冷却策略，用来降低误发与投诉，不用于规避平台检测。
- 不实现批量陌生人触达、自动加好友、隐蔽群发或绕过用户退订。

## “内置微信”的产品形态

工作台内提供：

- 多账号舰队：实例、Windows 会话、窗口绑定、在线状态、待审批数量和隔离任务。
- 统一会话：按账号筛选现有 `ConversationWorkbench`，不复制一套聊天系统。
- 人工接管：定位并唤起对应官方微信窗口，同时暂停该账号自动队列。
- 实例设置：复用现有 `PersonalWechatInstancesPanel` 完成实例验证、保存和停用。
- 合规检查器：身份证据、窗口证据、人工审批、发送预算、退订和审计事件。

工作台不直接显示或控制微信密码、二维码登录凭据，不注入微信进程，不修改客户端，不使用协议逆向。

## 语音方案

允许三种模式：

1. 操作员真人录音：操作员本人录制、预览并人工发送。
2. 语音转文字：操作员口述后生成文字草稿，人工校对后进入正常回复审批。
3. 授权合成语音：使用企业拥有合法授权的中性品牌音色，永久显示“AI 合成语音”，记录生成来源、审批人和发送人。

不实现未经授权的声音克隆、冒充某位员工或客户、隐藏合成语音来源。合成语音可以有自然停顿、语调和情感，但必须保持身份透明，不能以“让客户误以为是真人”为验收目标。

## 最小 UI 模块

```text
features/integrations/
  personal-wechat-control-page.tsx              # 账号状态与入口
  personal-wechat-voice-assist-page.tsx         # 语音辅助（未启用）
  personal-wechat-voice-assist-model.ts          # fail-closed 条件模型
  personal-wechat-voice-assist-stages.tsx        # 只读流程预览
  personal-wechat-safety-page.tsx                # 发送安全证据
```

这些模块必须是受控 React 组件，不在挂载时发送消息。`page.tsx` 只负责数据适配和组合，真实发送与权限判断始终留在 API 服务端。语音辅助路由当前没有控制器、录音或审批 API，默认 `enabled=false` 且不传入任何 actions，因此所有动作保持禁用；不能把流程预览描述成已可完成审批。

## 验收条件

- 初始真实发送状态为关闭。
- 每个账号都能看到独立 Windows 会话、端点和窗口绑定状态。
- 同一 Windows 会话中的两个账号不能显示为可并行发送。
- 人工接管后该账号的自动队列暂停。
- 所有回复经过身份、窗口、最近消息和人工审批检查。
- `uncertain` 任务没有自动重试按钮。
- 语音转文字可以编辑；合成语音必须显示 AI 标识并经过人工批准。
- 账号、客户、会话和语音草稿切换时不能串号。
- 所有启用、审批、拒绝、阻断、接管和停止动作都有审计事件。
- 1536px 与 390px 均无横向溢出，移动端一次只显示一个主要 pane。
